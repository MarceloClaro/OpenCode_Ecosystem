\section{Paradigma de Pesquisa: Design Science Research}

Esta pesquisa adota o paradigma de Design Science Research (DSR), conforme formulado por Hevner et al. (2004) \doi{10.2307/25148625} e refinado por Peffers et al. (2007) \doi{10.2753/MIS0742-1222240302}. O DSR é particularmente adequado para pesquisas que produzem artefatos de software como contribuição principal, pois enfatiza a criação e avaliação de artefatos destinados a resolver problemas identificados.

\subsection{Ciclo DSR Adotado (Peffers et al., 2007)}

O ciclo de 6 etapas de Peffers et al. (2007) foi seguido rigorosamente:

\begin{enumerate}
    \item \textbf{Identificação do problema}: O Scanner Pipeline diagnosticou 4 gaps críticos. Documentado na architectu-008.
    \item \textbf{Definição dos objetivos}: Para cada gap, uma SPEC formal foi escrita (SPEC-033, SPEC-036, SPEC-037, SPEC-038).
    \item \textbf{Design e desenvolvimento}: Cada SPEC $\rightarrow$ CTs (Red) $\rightarrow$ Implementação (Green) $\rightarrow$ Refactor.
    \item \textbf{Demonstração}: O artefato foi usado para resolver o problema que o originou — auto-diagnóstico funcional.
    \item \textbf{Avaliação}: 312 CTs, 8.034 eventos JSONL, 23 ciclos de evolução.
    \item \textbf{Comunicação}: Dissertação + GitHub + ADRs + SPEC\_COVERAGE.md.
\end{enumerate}

\section{Spec-Driven Development (SDD)}

\subsection{Estrutura de uma SPEC}

Cada especificação formal segue uma estrutura padronizada de 8 seções: Status, Problema, Conceito, Estrutura de Dados, Interface Pública, Critérios de Aceitação (CTs), Integração (dependências), e Referências. O template garante que todas as SPECs sejam comparáveis e auditáveis.

\textbf{Exemplo — SPEC-033 (Composição Unitária)}: Documento de 290 linhas definindo o modelo formal $C = E + S + R$, as estruturas CognitiveInput e CapabilityUnit, a biblioteca de 85 insumos, e 8 CTs originais (expandidos para 13 na implementação).

\subsection{Relação entre SPECs e Módulos}

Cada módulo Python é vinculado a exatamente uma SPEC. Módulos sem SPEC (audit\_refinements.py, interaction\_logger.py, etc.) são considerados auxiliares e não requerem especificação formal. A Tabela~\ref{tab:spec_modules} mapeia as 13 SPECs aos 22 módulos.

\section{Test-Driven Development como Método Científico}

\subsection{Fundamentação Epistemológica}

O TDD pode ser interpretado como uma instância do método científico aplicado à engenharia de software (Janzen \& Saiedian, 2005) \doi{10.1109/MC.2005.314}. Esta interpretação é fundamentada no falsificacionismo de Popper (1959): uma teoria científica nunca é provada verdadeira, apenas corroborada após resistir a tentativas de refutação.

No contexto do OpenCode, cada CT é uma hipótese falseável sobre o comportamento do sistema. A Tabela~\ref{tab:tdd_epistemologia} mapeia os conceitos epistemológicos aos elementos do TDD.

\begin{table}[H]

\textbf{Conceito Epistemológico} & \textbf{Elemento do TDD} \\
\midrule

Refutação & CT falha $\rightarrow$ hipótese rejeitada \\

\subsection{Estrutura de um Critical Test}

Cada CT no OpenCode segue uma estrutura padronizada que retorna um objeto \texttt{CTResult} com: \texttt{ct\_id} (identificador único vinculado à SPEC), \texttt{name} (descrição legível), \texttt{passed} (booleano), e \texttt{detail} (evidência textual auditável).

\section{Ciclos Evolutivos como Unidade de Análise}

Cada ciclo evolutivo (R1-R23) constitui uma unidade de análise independente, documentada com: diagnóstico (gaps identificados), planejamento (CPs selecionados), implementação (módulos criados), validação (CTs aprovados), e documentação (ADRs, SPECs atualizadas).

A progressão documentada (R1=85 $\rightarrow$ R23=100, +17.6\%) demonstra melhoria consistente. A métrica de score é composta por: cobertura de testes (40\%), cobertura de documentação (30\%), inovação (20\%), e estabilidade (10\%).

\section{Métricas de Validação}

\subsection{Métricas Primárias}

\begin{itemize}
    \item \textbf{Critical Tests (CTs)}: 312 testes cobrindo 100\% dos módulos. Critério de aceitação: 100\% passam, zero regressão.
    \item \textbf{Observabilidade}: 8.034 eventos JSONL com timestamps ISO 8601.
    \item \textbf{Cobertura de documentação}: 100\% dos módulos com SPEC formal.
\end{itemize}

\subsection{Métricas Secundárias}

\begin{itemize}
    \item \textbf{Complexidade ciclomática} (McCabe, 1976): média 4.2/função (limite recomendado: 10).
    \item \textbf{Coesão}: Single Responsibility Principle — cada módulo tem exatamente uma responsabilidade.
    \item \textbf{Acoplamento}: Dependências explicitamente declaradas via imports e documentadas nas SPECs.
\end{itemize}

\section{Considerações Éticas e Reprodutibilidade}

Esta pesquisa não envolveu seres humanos, animais, ou dados pessoais. O artefato é open-source (Apache 2.0). A reprodutibilidade é garantida por: ambiente documentado (Windows 11, Python 3.12), seed fixa (42) para testes não-determinísticos, ordem determinística de execução, e ambiente limpo a cada execução. O comando \texttt{python specs/test\_*.py} reproduz todos os 312 resultados.
