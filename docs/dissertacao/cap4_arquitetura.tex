\section{Princípios Arquiteturais}

A arquitetura do OpenCode Ecosystem foi projetada seguindo cinco princípios fundamentais, derivados da literatura de engenharia de software. Gamma et al. (1994)\citecrit{%
Design patterns capture solutions that have developed and evolved over time. They reflect untold redesign and recoding as developers have struggled for greater reuse and flexibility in their software.}{%

Fundacional. Gamma et al. Os cinco princípios são:

\begin{enumerate}
    \item \textbf{Separação de responsabilidades}: cada camada tem uma responsabilidade única. A L1 (Skills) não conhece a L7 (Trust Engine). A complexidade de cada camada é isolada.
    \item \textbf{Inversão de dependência}: camadas superiores dependem de abstrações. O \texttt{MetacognitiveMonitor} depende da interface \texttt{scan\_output}, não de um scanner concreto.
    \item \textbf{Observabilidade}: todo componente expõe métricas. Os 8.034 eventos JSONL materializam este princípio.
    \item \textbf{Testabilidade}: todo componente pode ser testado isoladamente. As 15 suites TDD (312 CTs) são a evidência.
    \item \textbf{Evolutibilidade}: a arquitetura suporta novas camadas sem modificar existentes. Os 23 ciclos demonstram este princípio.
\end{enumerate}

\section{As 7 Camadas}

\begin{enumerate}
    \item \textbf{L1 — Skills (161) + Infraestrutura}: Documentos de procedimentos reutilizáveis + Node.js 22 LTS, Bun 1.3, Python 3.12.
    \item \textbf{L2 — MCPs (46 servidores)}: Ferramentas externas via Model Context Protocol. Buscadores, navegadores, bancos de dados.
    \item \textbf{L3 — Agentes (128)}: Executores especializados. Coordenados pelo Nexus NMA v6.2.
    \item \textbf{L4 — Scanner Pipeline (M0-M5)}: Diagnóstico epistemológico. Identifica gaps, decompõe capacidades, gera roadmaps.
    \item \textbf{L5 — MCSP}: Encontra conjunto mínimo de capacidades otimizando cascade\_impact / construction\_cost.
    \item \textbf{L6 — Metacognição}: Auto-observação, detecção de anomalias, correção, síntese, governança.
    \item \textbf{L7 — Trust Engine}: Prevenção. Behavioral Gate decide se ações devem ser executadas.
\end{enumerate}

\section{Fluxo de Execução: O Pipeline M0-M7+Gate}

O pipeline completo segue a sequência M0$\rightarrow$M7 com o Gate (L7) atuando como pré-condição. A execução de uma ação $a$ segue o protocolo:

\begin{equation}
\text{executar}(a) = \begin{cases}
\text{prosseguir}(a) & \text{se Gate}(a) = \text{allowed} \\
\text{bloquear}(a) & \text{caso contrário}
\end{cases}
\label{eq:gate_protocol}
\end{equation}

Onde $\text{Gate}(a)$ consulta o \texttt{TrustScorer} e retorna uma \texttt{GateDecision} com a classificação de risco. Após a execução, o outcome é registrado via $\text{learn}(a, \text{success}, \delta)$, fechando o ciclo de aprendizado.

\section{Mecanismo de Comunicação: Pub/Sub Assíncrono}

A comunicação entre camadas segue o modelo publish-subscribe, escolhido sobre chamadas síncronas por três razões: desacoplamento temporal (camadas não precisam estar ativas simultaneamente), auditabilidade (todo evento é registrado com timestamp), e extensibilidade (novas camadas assinam eventos existentes sem modificar publicadoras).

A formalização do modelo é:

\begin{equation}
E = \{(t, s, p) \mid t \text{ é timestamp}, s \text{ é source}, p \text{ é payload}\}
\label{eq:event_stream}
\end{equation}

Onde $E$ é o stream de eventos JSONL. Subscribers consultam $E$ para reconstruir o histórico de qualquer execução.

\section{Decisões Arquiteturais (ADRs)}

As 10 ADRs documentam decisões críticas com contexto, alternativas e justificativa. Cada ADR segue o template: Contexto $\rightarrow$ Decisão $\rightarrow$ Alternativas Consideradas $\rightarrow$ Consequências $\rightarrow$ Status.

\begin{enumerate}
    \item \textbf{architectu-001 — Token Budget}: Limite de tokens por operação. Monitorado pelo \texttt{token\_economy\_monitor.py}.
    \item \textbf{architectu-002 — Three-Layer}: Separação MCP$\rightarrow$Skill$\rightarrow$Agent permite evolução independente.
    \item \textbf{architectu-003 a 007}: SPECs 019-031 (API Governance, Streaming, Low-Code, Token Economy, Scanners).
    \item \textbf{architectu-008 — Composição Unitária}: Decomposição de capacidades. Modelo $C = E + S + R$, CognitiveInput, CapabilityUnit.
    \item \textbf{architectu-009 — Integração Stage 3}: CapabilityComposer como M3.5 com campos opcionais.
    \item \textbf{architectu-010 — Metacognição}: Camada L6 separada seguindo padrão Observer.
\end{enumerate}

\section{Infraestrutura de Testes}

A infraestrutura de testes é integrada à arquitetura. Cada módulo tem SPEC formal, suite TDD, e log JSONL. O gate de CI/CD exige 100\% de aprovação antes de cada commit. A cobertura de testes é quantificada por:

\begin{equation}
\text{cobertura} = \frac{|\text{módulos com } \geq 1 \text{ suite TDD}|}{|\text{módulos totais}|} = \frac{22}{22} = 1.0
\label{eq:coverage}
\end{equation}
